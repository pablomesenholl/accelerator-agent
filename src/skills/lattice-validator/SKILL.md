# Lattice Validator

## Overview

This skill validates a prepared OPALX simulation input generated by the `lattice-generator` skill before it is passed to the `opalx-simulator` skill. The input may be a single `.in` file or a simulation directory containing the main input file and supporting files.

Validation has four layers: native OPALX syntax validation, structural and semantic checks, specification consistency, and basic physics sanity checks. The skill **does not generate or modify inputs, run particle tracking, or perform advanced accelerator-physics design**.

- Use the `lattice-generator` skill to correct invalid inputs.
- Use the `magnus` skill for blueprint invocation, job status, logs, and backend errors.
- Use the `opalx-simulator` skill only after validation succeeds.
- Delegate nontrivial beam-optics calculations or physics design to a dedicated accelerator-physics skill when available.

Before writing reports, follow the shared [run layout](../references/run-layout.md) and retain the run ID supplied by the preceding stage.

## Inputs

- `simulation` — path to a prepared OPALX `.in` file or simulation directory.
- `input_file` — main `.in` filename or path relative to `simulation` when it is a directory.
- **Original specification** — the user's requested lattice, beam, and simulation settings, plus the generator's documented assumptions and defaults when available.

The input paths should remain compatible with the `opalx-simulator` skill. If the original specification is unavailable, specification consistency cannot be verified and full validation is `INCONCLUSIVE` unless another layer establishes `FAIL`.

## Outputs

Save the validation report to `output/<run-id>/progress/validation.md` and return its path with the run directory. Include:

- **Status:** `PASS`, `FAIL`, or `INCONCLUSIVE`.
- **Validated input:** simulation path and relative main `.in` path.
- **Checks performed:** which validation layers completed and their outcomes.
- **Issues:** errors and warnings, with file/statement location and suggested correction where possible.
- **Handoff decision:** whether the input may proceed to `opalx-simulator`.

`PASS` means all required checks completed without blocking errors; it does **not** guarantee that tracking will succeed or that simulation results will be physically correct. `FAIL` means a blocking problem was found. `INCONCLUSIVE` means required checks could not be completed. Only `PASS` permits automatic simulation handoff.

## Workflow

### Step 1: Inspect the prepared input

Confirm that `simulation` and the main `.in` file exist. For a directory, verify that `input_file` is a relative path within that directory. Identify available supporting files and any supplied generation summary or original user specification.

Do not change the input files during validation.

### Step 2: Validate syntax using OPALX (Layer 1)

This step can be skipped for now as a parser only version of OPALX is not implemented yet.

(Invoke the planned **parser-only OPALX validation** through the `opalx-validation` Magnus blueprint. This blueprint is expected to parse the complete input without executing particle tracking.

Before invocation, confirm that the blueprint is registered and inspect its actual parameter schema:

```bash
magnus blueprint schema opalx-validation
```

Pass the prepared simulation and main input path according to that schema. Use the `magnus` skill to examine the job result and OPALX parser diagnostics, including exit status and error locations.

- If parsing fails, record the syntax errors and mark validation `FAIL`.
- If the blueprint is unavailable, fails operationally, or does not establish that the full input was parsed, mark validation `INCONCLUSIVE` unless another check already establishes `FAIL`.
- Do **not** substitute a normal OPALX simulation run for parser-only validation.

**Implementation dependency:** The OPALX parser-only feature and corresponding Magnus blueprint must be implemented and registered before this layer can pass.)

### Step 3: Check structural and semantic consistency (Layer 2)

Inspect the input and its supporting files using available filesystem tools and OPALX documentation. Check, as applicable:

- References to defined beamlines, elements, beams, distributions, sources, and field solvers.
- Presence and correct relative paths of required auxiliary files.
- Required configuration fields and clear numerical constraints (for example, positive element lengths and valid tracking limits).
- Known unsupported or incompatible OPALX features and settings.
- Variable definitions, global parameters, expressions, and consistency between dependent quantities.
- OPALX-specific parameter conventions and potentially problematic redefinitions or implicit defaults.

Use current OPALX behavior as the reference; do not assume that legacy OPAL input is supported. Distinguish definite errors from configurations that merely require further investigation.

### Step 4: Check specification consistency (Layer 3)

Compare the generated input with the original user request. Verify that requested lattice elements and ordering, beam parameters, distributions, simulation settings, and diagnostics are correctly represented. Identify missing requirements, altered values, and unrequested physical assumptions or effects.

Distinguish user-specified values from documented derivations and technical defaults. Flag discrepancies for correction or clarification; do not silently reinterpret the request. If the original specification is unavailable, this layer is incomplete.

### Step 5: Check basic physical consistency (Layer 4)

Check obvious physical plausibility and consistency, such as units, particle species and reference momentum, magnet strengths, and field-solver assumptions. A configuration can be physically plausible yet fail specification consistency.

Treat unusual but intentional configurations as potentially valid. Do not require matched Twiss parameters, stable optics, or optimized beam dynamics unless explicitly requested. Do not invent missing physical parameters or redesign the lattice; flag questions that require user clarification or a future accelerator-physics skill.

### Step 6: Report and hand off

Summarize each layer's result and classify issues as **blocking errors** or **warnings**. Return `PASS` only when required validation is complete and no blocking issue remains.

For `PASS`, return the unchanged input paths for the `opalx-simulator` skill. For `FAIL` or `INCONCLUSIVE`, do not launch the simulation; report the problem and the next action needed.

## Usage

Invoke this skill after `lattice-generator` prepares a simulation and before `opalx-simulator` runs it. Use the same `simulation` and `input_file` identifiers across the handoff. The exact `opalx-validation` command arguments must be taken from its registered Magnus schema once available.

## Error Handling

When validation finds a correctable input error, return the diagnostic and proposed correction to `lattice-generator`. The generator owns modifications; validate the updated input again before proceeding.

- **Syntax or missing-reference error:** Identify the affected statement or file and request a targeted correction.
- **Unsupported configuration:** Explain the incompatibility; do not silently replace the requested physics with another model.
- **Specification mismatch:** Identify missing, altered, or unrequested settings and ask `lattice-generator` to reconcile the input with the original request.
- **Ambiguous physics:** Report the concern and request clarification or suitable physics expertise rather than guessing.
- **Magnus or parser infrastructure failure:** Report `INCONCLUSIVE` and diagnose via the `magnus` skill; do not treat it as an input error.

Avoid repeated submission of unchanged failing inputs. Limit autonomous repair attempts (initially three); if errors persist, stop and present the diagnostics for review. Preserve user-specified physics parameters unless the user authorizes changes.

## Examples

### Valid FODO input without space charge

Validate a generated FODO simulation directory. Confirm that native parsing succeeds, dependencies and configuration are consistent, and the model agrees with the supplied FODO specification. Return `PASS` and the unchanged paths if no blocking issues are found.

### Invalid reference in a lattice

If the input refers to an undefined element or beamline, return `FAIL` with the relevant location and a suggested correction. Ask `lattice-generator` to fix the reference and repeat validation; do not edit the file in this skill.
